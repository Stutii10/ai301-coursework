# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record (OS, runtime/language version or release version, repo commit/branch if applicable), read against the issue's own stated environment (issue body or repo-facts block) | PASS if the record states OS, a version identifier (a git commit/branch, OR a release/package version number when the project is consumed as a released package rather than a git checkout), AND any difference from the issue's stated environment is explicitly named. FAIL if a real mismatch is present but unmentioned, or if the record is missing OS or any version identifier entirely. | required |
| steps-followable | The repro report's steps section, from starting state through the point the bug triggers | PASS if every command actually executed is given as a literal, copy-pasteable command (not paraphrased as "then run the tests"), AND the starting state is explicitly and unambiguously described — supporting input (a config file's content, a script's content) may be described in clear prose rather than pasted verbatim, as long as the description is specific enough that a stranger could recreate it without guessing. FAIL if the starting state is missing entirely, if an executed command is paraphrased instead of literal, or if a described (non-literal) input is vague enough that a stranger could not recreate it. | required |
| behavior-matches-issue | Artifacts in the repro report (output excerpts, stack traces, logs, screenshots) or an explicit non-reproduction result, read against the issue's own description of the bug | PASS if the artifact shows the same error type and message text the issue describes or quotes (allowing incidental differences like line numbers from a disclosed environment difference), OR if the report honestly states it could not reproduce the issue and shows evidence of a genuine, on-target attempt (steps tried, what was expected, what happened instead, and what may differ from the issue's conditions). FAIL if the artifact shows a different error, a different code path, or a plausibly-adjacent but distinct failure presented as a match — this is a clear reject, not unclear. An unevidenced or vague non-reproduction (no real attempt shown) also FAILs. | required |
| honest-claims | The report's stated conclusion/summary language, read against its own artifacts and steps | PASS if every claim of certainty is backed by an artifact that shows it, AND anything not fully certain is explicitly flagged as such. An honest, evidenced "could not reproduce" is a full PASS. FAIL if a guess or unconfirmed claim is presented as settled fact without being flagged, even if it turns out correct. | required |
| ai-disclosure | The claim comment and repro comment text, read against the repo's stated contribution policy/templates for AI-use disclosure requirements specifically | PASS if the repo's policy does not require a positive disclosure statement about AI use (a policy that merely requires comments be written in the contributor's own words, or bans low-quality/undisclosed wholesale AI authorship, is NOT a disclosure requirement and auto-passes this check), OR if it does require disclosure and the comment contains any clear mention that AI/Claude assistance was used. FAIL only if the policy explicitly asks contributors to state whether/how AI was used, and the comment contains no such statement. | required |

## Verdict rule

Accept (ready to post) if and only if every required check passes. A single required fail or unclear produces a reject (hold).

unclear is treated as fail for every required check: if the evidence needed to judge a check cannot be found or verified, don't post.
